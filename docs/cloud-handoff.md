# Keyball61右側復旧の引き継ぎ

更新日: 2026-10-18

## 目的・背景

右側マイコン交換後、右側の全キーが無反応になったKeyball61を復旧します。左ボール構成で、左側がCentral、右側がPeripheral、左右ともSuperMini NRF52840です。左側の文字入力・USB/Bluetooth・トラックボールを維持することが条件です。

- リポジトリ: https://github.com/mieze018/zmk-config-Keyball61
- 正常構成の保護対象: `leftball`
- 診断ブランチ: `codex/right-recovery-usb-logging`
- 作業詳細: [USBログ診断の記録](right-recovery-usb-logging.md)
- ZMK v0.3、Zephyr v3.5.0+zmk-fixes。実際の取得リビジョンとUF2ハッシュは上記記録を参照してください。

## 確認済みの現在地

| 項目 | 結果 |
|---|---|
| 左側の文字入力・トラックボール | 診断UF2書き込み後も動作するとのユーザー確認あり |
| 左側からMacへのBluetooth入力 | 動作するとのユーザー確認あり |
| 左右のBLE認証 | 右側だけの設定初期化後、ペアリング成功・暗号化成功・security level 2をログで確認 |
| 右側の文字入力 | 左側がMacへ接続済みでも、全キー無反応 |
| 右側GPIO設定 | 入力5本・出力7本の設定API成功ログあり |
| 全キー押下中の右側ログ | ライブ監視で受信0バイト・キーイベント0件。ただしログ受信そのものの問題があるため、これだけでスキャン停止や断線を確定しない |
| 右側OLED | 未接続。SSD1306初期化・I2Cのエラーあり。キー無反応との因果関係は未確定 |

BLE復旧前は右側がペアリング要求を受けた直後に `peer reason 0x03` / `Security failed ... level 1 err 4` で拒否していました。検証済みのsettings_reset UF2を右側だけへ書き込み、10秒通電後、右側ペアリング詳細ログ版へ戻すことで解消しました。保存設定が影響していたことは確認できましたが、古い鍵の内容や拒否分岐を直接観測したわけではありません。両側の初期化を無根拠に繰り返さないでください。

## 物理診断と測定結果

旧マイコン取り外し時にGND・10/B6付近のランド損傷があったとの引き継ぎがあります。GNDとRSTはジャンパー修復済み。新マイコンは起動・UF2書き込みが可能で、異常発熱は報告されていません。

ユーザーが測定した区間は、**マイコンのハンダから、その真裏のメイン基板パッドまで**です。基板側ではコンスルーピンに触れないように測っています。大半で導通を確認済みです。スイッチ・ダイオードまでの配線は未確認です。

直近の測定はUSB・バッテリー電源OFFで実施しました。

| 測定 | 結果 | 判断の限界 |
|---|---|---|
| テスターの先端同士 | ブザーあり、表示000 | 導通検出と表示変化は確認済み。繰り返し要求しない |
| `D4/4`裏側パッドから、マイコン直左の最上段キーの上にあるダイオードの両端 | 両方ブザーなし、表示1 | 実物での行の対応は未確定。断線とは断定しない |
| そのダイオード右端から、1つ左隣の最上段キーのダイオード右端 | ブザーなし、表示1 | 同じ配線だと確認せず指定した測定。断線の判定に使わない |
| 同じ最初のダイオードの両端から `C6/5`・`D7/6`・`E6/7`・`B4/8` の裏側パッドへ、計8通り | 全て無反応とのユーザー報告（2026-10-18） | 実物の対象部品・配線対応・接触点をまだ確定できていない |

公開の[Keyball61右側KiCadデータ](https://github.com/Yowkees/keyball/blob/main/keyball61/design_data/keyball61_Right_KiCad.zip)をプログラムで読み、ProMicroのD4・C6・D7・E6・B4に対応する行配線を確認しました。ただし実物への位置対応を完了したわけではありません。ダイオードは取り付け向きによって共通側が変わるため、写真上の左右だけで決めないでください。

基板はAliExpressで購入。ユーザーはメイン基板が標準Keyball61と同じと考えています。販売ページのURLは未取得です。写真にはVBATコネクター、電源スイッチ、ProMicro用の印字、複数タイプのスイッチ用ソケットが写っています。写真だけで標準版と同一／別物とは断定していません。

## クラウドでの再開手順

1. GitHubへアクセスできるクラウド環境で診断ブランチを取得し、このファイルと作業詳細を読みます。
2. ユーザーに測定を繰り返させる前に、確定した事実・仮説・不確かな測定点を区別します。
3. 必要であればユーザーへ写真の再添付を依頼します。写真はGitHubへ公開していません。
4. 実物に対応する接続先を、回路図・基板データ・写真で確定するか、確定できない点を明示して接続関係を調べる測定を計画します。
5. 根拠を示して測定を1段階ずつ依頼します。配線変更・はんだ付けは原因を絞るまで提案しません。

## 注意点

- ローカルの写真は `/Users/nakataayu/Downloads/IMG_6211.JPG` と `IMG_6214.HEIC`。クラウドからこれらのMac上のパスを直接読むことはできません。
- クラウド環境には、これまでのUSBポートやMac上のログ取得プロセスがそのまま移るわけではありません。ログが必要ならユーザーに取得して添付してもらいます。
- UF2のダウンロード先として以前案内した `/private/tmp/` のパスもMac上のものです。クラウドではActions成果物から取得します。
- 実機への書き込み・リセット・物理測定はユーザー自身が実施します。
- ユーザーはマイコンから裏パッドまでの導通を既に測定しています。その測定やテスター先端同士の確認を不用意に繰り返させないでください。
- `Ctrl-A`等はMac本体のキーボードで操作するショートカットです。故障中の右側Keyballへ操作を要求しないでください。
- 過去の「キーイベント0件」だけを根拠にハードウェア故障を断定しないでください。USBログ受信の信頼性に未解決事項があります。

## トラブルシューティング

- **USBログ0バイト:** ユーザー実行の取得スクリプトはDTR明示後も0バイトになる事例があり、完全には解決していません。担当AIが起動後のポートを開き直すとログを取得できた事例があります。同じ手順を何度も依頼しないでください。
- **ポートが存在しない:** Macのポート名は抜き差しで変わります。過去の固定名を再利用しないでください。
- **認証失敗が再発:** まず接続先アドレスとエラーを確認し、Mac側HIDの接続と左右間接続を区別します。初期化を自動で繰り返しません。
- **測定値1・ブザーなし:** 測った2点の接続が本来保証される資料がなければ、断線の判定には使えません。テスターの先端同士では000・ブザーありを確認済みです。
